### R3-P0-1 磁盘空间零检查

- 问题：从分片写入到合并，后端没有任何一处检查磁盘剩余空间；`files/` 所在盘可用 57.2GB 而单文件宣称支持 30GB，空间不够时要等合并失败才知道，白传几十分钟。
- 原因：主路径（分片上传）从未接过磁盘检查——原先唯一有检查的 `/api/upload` 是死代码，删掉时缺口彻底暴露。
- 解决方法：(1) 后端新增 `GET /api/disk`，返回 `FILES_DIR` 所在盘的 `free` / `total`（字节）；(2) 前端 `uploadFiles` 开始前取一次，需求量按"本批总大小 + 最大文件大小"再乘 1.05 估算（合并期间分片与成品短暂并存，峰值多占一份；5% 是余量），不够就提示「服务器剩余空间不足：本次约需 X，当前可用 Y」并一个分片都不发；(3) 文件管理卡片新增「服务器剩余空间」显示（低于 10GB 标红），随 `loadFiles` 一起刷新。
- 日期：2026-09-20
- 验证：`/api/disk` 返回值与 `shutil.disk_usage` 实测一致（误差 <4KB）；浏览器页面显示「服务器剩余空间: 57.20 GB / 100.98 GB」，上传 40MB 后变为 57.21 GB；预检判定逻辑实测——60GB 文件 + 1KB 计算 required=135.3GB > free=61.4GB → 拒绝。

### R3-P0-3 分片上传的错误文案到不了用户

- 问题：重试链把首次失败的错误替换成"分片 N 重试失败"，最终界面只显示"部分分片上传失败"；`uploadChunk` 对非 200 也只产生 `HTTP 400` 不带服务端 `error` 文案。服务端任何拒绝（磁盘不足、参数不合法）用户都看不到原因。
- 原因：`uploadAllChunks` 的 catch 链逐层包装错误对象；批处理总结又只数成功失败个数。
- 解决方法：(1) `uploadChunk` 非 200 分支解析响应体 JSON 的 `error` 拼进错误信息（`HTTP 400：参数不合法`）；(2) 重试链记 `firstError`，第二次重试仍失败时**抛 `firstError`**（首个原始错误，不抛包装话术）；(3) 批处理失败总结附首个原因：「批量上传完成：成功 0 个，失败 1 个（首个原因：…）」。
- 日期：2026-09-20
- 验证：浏览器端到端——用非法 username 触发每个分片 400，界面最终显示「批量上传完成：成功 0 个，失败 1 个（首个原因：HTTP 400：参数不合法）」，服务端原文完整到达用户。中途发现并修正两处：firstError 原先在 `processNext` 抛出前根本没被使用（改为内层重试失败时直接抛 firstError）；批处理总结原先会立刻覆盖单文件错误文案（改为带上首个原因）。

### R3-P1-1 取消按钮会误删正在上传的分片

- 问题：`transferXhrs` / `transferCancelled` / `activeTransferId` 三个模块级单例被并发传输互相覆盖；"上传中点下载→再点取消"会拿残留的上传 file_id 调 `/api/upload/abort`，把正在上传的分片删掉，上传以"分片不齐全"失败。
- 原因：传输状态用多个全局变量表示，第二次传输开始时直接覆盖。
- 解决方法：收进单一 `currentTransfer = { kind, xhrs, cancelled, fileId }`；`cancelTransfer()` 只作用于它，且仅 `kind === 'upload'` 才调 abort 接口；`uploadFiles`、`uploadSingleFile`（防批量间隙插入）、`downloadFile` 三处入口在已有传输时提示「已有传输进行中」并拒绝（拖拽路径经 `uploadFiles` 一并覆盖）；各终态仅在"自己仍是当前传输"时清空。
- 日期：2026-09-20
- 验证：浏览器实测——伪造进行中的 download 传输后调 `cancelTransfer()`，拦截 fetch 确认**没有**发出 `/api/upload/abort`；忙时调 `downloadFile` 立即显示「已有传输进行中」；上传成功/失败后 `currentTransfer` 均正确清空。`grep` 确认三个旧全局变量在前端已零引用。

### R3-P1-2 `total_chunks` 无上限

- 问题：merge 校验用 `indices != list(range(total_chunks))` 会真的物化 list，而入口只校验 `>= 1`；实测 1e7 片 0.36s、线性外推 2e9 片要分配约 70GB，畸形请求可让服务端 MemoryError / 疯狂换页。
- 原因：入口校验没有上限。
- 解决方法：入口改为 `1 <= total_chunks <= 4096`（30GB/32MB 分片实际只需 960 片，4096 留足余量），超出返回 400「total_chunks 缺失或超出范围」。
- 日期：2026-09-20
- 验证：`total_chunks=4097` 与 `5000000` → 400 超出范围；`4096`（上限内、空分片）→ 400「分片不齐全: 期望 4096 片，实收 0 片」——上限与齐全性两道校验各自生效。

### R3-P1-3 merge 失败路径会删掉别的传输的文件

- 问题：`exclusive_path` 返回路径与 `open('xb')` 之间有竞态窗口，同秒同名并发 merge 时后到方抛 `FileExistsError` 进入 except，里面的 `os.remove` 删掉的是先到方的文件，且后到方分片被无条件清理、整次上传白费。
- 原因：except 无条件删 `exclusive_path` 选中的路径——它可能是**别人**刚创建的；撞名也被当成数据错误处理。
- 解决方法：merge 主体改循环——`FileExistsError` 单独接住并**重挑候选名重试**（分片未动，上传不丢）；其余异常（open 成功后的写入失败，如磁盘写满）才走清理半成品路径，此时删的必是自己创建的文件。
- 日期：2026-09-20
- 验证：进程内确定性测试——monkeypatch `exclusive_path` 让第一次返回的候选路径被"并发方"抢先创建：先到方文件 `inproc.bin`（内容 winner-data）**未被删除**；后到方自动改名 `inproc_1789809231.bin` 合并成功、内容与 SHA-256 均正确。

### R3-P2-1 JSON 接口与首页无 `Cache-Control`

- 问题：首页与 JSON 接口无缓存头，浏览器启发式缓存/后退前进缓存可能给出旧页面旧列表（"改了没生效"类困惑）。
- 原因：`after_request` 只记日志，从未设置缓存策略。
- 解决方法：`after_request` 里按**请求路径**设置——`/` → `no-cache`；`/api/*` 但排除 `/api/download` 与 `/api/download/chunk` → `no-store`（这两个路径的 ETag/Last-Modified 是断点续传依赖，不能覆盖）。
- 日期：2026-09-20
- 验证：`GET /` → `Cache-Control: no-cache`；`GET /api/files` → `no-store`；`GET /api/download` → 保持 Werkzeug `send_file` 原生的 `no-cache` + ETag + Last-Modified 不变（对照旧代码 `be6961d` 实测确认该头本就存在，本次改动没有碰它），`Range` 请求仍 206。
- 备注：原方案按 `resp.mimetype == 'application/json'` 判断会误伤 `.json` 文件的下载（其 mimetype 恰为 application/json），已按路径判断规避。

### R3-P2-2 对账读改写哈希记录未加锁

- 问题：启动对账线程读改写 `.hashes.json` 未持 `_hash_lock`，与并发上传的 `record_hash` 存在丢更新窗口（新记录被旧快照覆盖）。
- 原因：对账直接写手里那份启动时读出的快照。
- 解决方法：哈希重算全部在锁外完成（`hash_file` 可能读几十秒）；有变更时进锁 → **重新 `read_hashes`** → 合并删除项与补算项 → 写出。
- 日期：2026-09-20
- 验证：进程内调用 `reconcile_hashes()`：「校验码对账完成: 补算 0 个, 清理 0 条, 失败 0 个目录, 耗时 0.00s」，4 条既有记录（e2e.bin / hdr.bin / it's & test #1.txt / space tail）完好。

### R3-P2-3 下载吞吐无记录

- 问题：`after_request` 在响应体迭代前执行，`/api/download/chunk` 耗时永远记 0.0x s；分片日志降 DEBUG 后连 Content-Length 也不留，"跑没跑满带宽"无法回答。
- 原因：访问日志的计时点选在了响应体开始流式发送之前。
- 解决方法：`generate()` 开头记 `time.monotonic()`，`finally` 里按 `sent >= length` 二选一记：完成 → INFO「下载完成: user/file/start/已发送/耗时/均速」；不足 → 原有的「下载中断」告警（互斥，不会同时出现）。
- 日期：2026-09-20
- 验证：curl Range 取 32MB，日志出现「下载完成: user=… file=e2e.bin start=0 已发送=32.00MB 耗时=0.15s 均速=211.9MB/s from=127.0.0.1」（curl 自测 219.6MB/s，同量级）。

### R3-P2-4 `safe_filename` 加固

- 问题：只挡分隔符/`..`/前导点。Windows 设备名（`NUL.txt` 在 Windows 上 `open()` 静默成功 → 上传假成功）、控制字符（拼进 Content-Disposition）、结尾点（Windows 静默归一化导致哈希记录键对不上）、超长名（路径破 260 OSError）都未挡。
- 原因：校验规则只覆盖了路径穿越一类。
- 解决方法：追加四条拒绝规则——任一控制字符（`ord(c) < 32`）；设备名（`filename.split('.')[0].upper()` 命中 `CON/PRN/AUX/NUL/COM1-9/LPT1-9`）；结尾点或空格（空格实际由既有的 `strip()` 归一化处理，点是显式拒绝）；长度 > 200。
- 日期：2026-09-20
- 验证：`NUL.txt` / `con` / `COM3.bin` / 含 `\x01` / `tail.` / 201 字符名全部 400；`a b.txt`、`it's & test #1.txt` 正常上传合并；`"space tail "`（尾空格）归一化为 `space tail` 上传成功。

### R3-P2-5 两处仍回显 `str(e)`

- 问题：`upload_merge` 与 `delete_file` 的 except 块把异常字符串回给客户端，泄漏服务器绝对路径（P2-17 修复时漏掉的两处）。
- 原因：当时只改了兜底 handler 与 chunk 接口。
- 解决方法：两处改为固定文案「合并失败，详情见服务端日志」/「删除失败，详情见服务端日志」，`log.exception` 堆栈不动。
- 日期：2026-09-20
- 验证：向 merge 发非法 JSON body（GBK 字节）→ 400 且响应体无路径；`grep str(e)` 确认仅剩 `:590` 的自产业务文案「分片不齐全」（按 P2-17 原则保留）。

## demo-v3 / portrait-noir-relay 功能补全

- 解决方法（生产页未动，仅 demo）：
