## 三轮评审收口：status 接口对畸形分片文件的处置实测（登记 P2-4，代码零改动）

- 问题：二轮评审把前端两处静默 catch 补了 `console.warn`（C-0926-7 同口径），但后端 `GET /api/upload/status` 里还有一处 `except: continue` 没登记——分片目录内出现名字不合规矩的 `chunk_*` 文件时，服务器不作声地把它滤掉，日志零线索。
- 原因：登记时漏了这一处；且合并接口对同一情况的处置此前只有静态推断，没跑过真实请求。
- 解决方法：5001 临时实例实测（一次性用户 `p2probe`，测完目录已删）：
  - 往 `.chunks/<file_id>/` 放 `chunk_0`(1024B) + `chunk_abc` + `chunk_` + `meta.json`，请求 status → **200**，`received` 只含 `[{index:0,size:1024}]`，`logs/app.log` 该请求上下文无任何 warning。
  - 同目录放两片 1MB 正常片 + 一个比正常片更大的 `chunk_`（骗过齐全性校验），请求 merge（total_chunks=2）→ **400**，错误文案是 Python 原始异常 `invalid literal for int() with base 10: ''`（不是项目友好文案），分片目录被整体删除（含 2 个完全正常的分片）；日志有 `WARNING 合并被拒(分片不齐)` 带原因。
  - 结论：正常前端操作造不出畸形文件（分片名恒为 `chunk_<整数>`，合并前必先查 status），最坏后果是"该 file_id 这次上传作废、从头重传"，不丢已落盘用户数据。按「代码评审分级」登记为 P2-4（`review-p2.md`），不修。
