## 留言板：删掉启动期的旧 `.txt` 兼容迁移

- 问题：`init_board()` 里带了 20 行"首次启动把 `clipboards/<user>.txt` 迁成留言并改名 `.migrated`"的逻辑，靠 `os.rename` 的原子性做多进程去重。用户要求去掉：**"直接迁移到sqlite中，系统不要做这种上级兼容的事情，写的代码越多，bug就越多。"**
- 原因：把一次性数据搬迁写进了服务启动路径——每个 worker 启动都要跑一遍 glob + rename + 读文件，多进程去重还得依赖 rename 语义，这些复杂度只为照顾三个早已没人读的文件。
- 解决方法：`init_board()` 只留 `PRAGMA journal_mode=WAL` + `CREATE TABLE IF NOT EXISTS`（`http_messages_share.py:150-166`，20 行 → 16 行）；启动日志文案从"建表/旧剪切板迁移"改成"建表"。旧数据用一次性脚本 `%TEMP%/qfs_oneoff_migrate.py` 导入后删除脚本。同步改了 `AGENTS.md`、`README.md`、`review-issues.md` 与 2026-09-21 归档里对这段逻辑的描述。
- 日期：2026-09-22
- 验证：脚本对真实 `clipboards/` 跑完——3 行入库（`d` 143 字、`logtest` 5 字、`用户` 5072 字节截到 2000 字），`SELECT COUNT(*)` = 3，三个 `.txt` 改名 `.migrated` 留在原地；`py_compile` 过；`grep 旧剪切板 http_messages_share.py` 零命中；`app.test_client()` 起 `GET /api/board?username=用户` → 200，返回 3 条（`latest_id=3`、`total=3`），三条 author 分别是 `d` / `logtest` / `用户`。

## 留言板：删除自己的留言 + 长留言折叠到 10 行

- 问题：板上贴了长文本（比如 2000 字的旧剪切板）就占满整屏，看不到下面几条；发错的留言也撤不掉，只能留着。
- 原因：`.clip-text` 没有行数上限，一条多长就铺多长；后端只有 `GET/POST /api/board`，没有删除入口。
- 解决方法：
  - 后端新增 `POST /api/board/delete`（body `{username, id}`）与 `delete_message(message_id, username)`（`http_messages_share.py:202-216`）：在 `_board_lock` 里先 `SELECT author` 比对，`author != username` 返回 `forbidden`（403「只能删除自己发送的留言」），查不到返回 `missing`（404「留言不存在或已被删除」），命中才 `DELETE`。`id` 必须是 ≥1 的整数否则 400。删除记 INFO「留言已删除: user=… id=…」，被拒记 WARNING。
  - 前端 `board.js`：`makeClip()` 每行分两块。`.clip-actions`（`margin-left:auto` 靠右）里先放可选的 `删除`（带 `.danger`，仅当 `m.author === ctxRef.getUsername()`）再放 `复制`，「复制」永远是最后一个、各行右边缘对齐；正文外面套 `.clip-body`（`position:relative`），里面是 `.clip-text.collapsed` + 一个默认 hidden 的 `.clip-more`「展开」。渲染完跑 `fitClamps()`，量 `.clip-text` 的 `scrollHeight - clientHeight > 1` 才把「展开」显示出来，不溢出的行直接摘掉 `.collapsed`；点「展开」切 `.collapsed`、文案换成「收起」。删除走 `removeMessage()`，成功后调 `reload()` 而不是 `load()`——删中间那条时 `latest_id` 没变，带 `after` 的轮询会被判成"没变化"，界面不刷新。`api.js` 加 `deleteBoard`（13 个接口）。事件仍是一个委托监听器，选择器 `.clip-actions .qbtn, .clip-more`。
  - CSS：`.clip-text.collapsed { display:-webkit-box; -webkit-box-orient:vertical; -webkit-line-clamp:10; overflow:hidden }`（行数只有这一处定义）。「展开」由 `.clip-text.collapsed + .clip-more` 定位到裁切块右下角、左侧一段 `linear-gradient` 渐隐压住第 10 行行尾；展开后选择器不再命中，按钮回到 `static` 流贴在正文下方一行。
- 日期：2026-09-22
- 验证：临时实例 5001（未占 5000），一次性用户 `pytest12`，测完已清干净（库里回到 3 条 `d`/`logtest`/`用户`）。接口：`用户` 删 `pytest12` 的那条 → 403；`pytest12` 删 id=1（用户 的）→ 403；`id="3"` / 缺 id / `username=../etc` → 400；本人删 → 200，再删 → 404。页面（1280 宽）：25 行留言 `clientHeight` 219px（= 10 行 × 21.875px）对 `scrollHeight` 1094px，`webkitLineClamp` 计算值 `10`，「展开」显示；点开→1094px 且文案变「收起」，再点回 219px；短留言（`d` 4 行、`logtest` 1 行）`scrollHeight == clientHeight`，`.collapsed` 被摘掉、无「展开」按钮；切到 `pytest12` 后只有它自己那行带「删除」，另三行没有；点删除 → 该行消失、toast「已删除」、`total` 从 4 回到 3。`py_compile` 与 12 个模块 `node --check` 全过。
- 同日二次实测（按钮对齐 +「展开」挪到行尾）：1280 宽下四行的「复制」右边缘都是 1240px，390 宽下都是 442px；「展开」右边缘同为 1240/442，底边与正文底边相等（贴在第 10 行行尾）；展开后「收起」计算值为 `position: static`、`moreTop == textBottom`（不与正文重叠），正文回到 1094px；390 宽 `scrollWidth - clientWidth == 0`（无横向溢出）。
- 说明：用户名是自选的、全站无鉴权，所以"只能删自己的"靠的是请求里带的 `username` 与 `author` 比对——它挡住误删，不挡住故意伪造，与整站的信任模型一致。

## 登录 → 主页转场：删掉金色揭示层，改用退出方向那套纯交叉淡入

- 问题：A1（2026-09-21）之后，用户仍然反馈点「进入」是"哗的一下的闪一下，中间还有停顿"。原时序 `login.js` 里三处 `later()`：0 提交 → 520ms 卡片离场 + 拱框苏醒 → 950ms 给 `.wash` 加 `revealing` 且同帧翻 `data-stage` → 1680ms 收幕。`.wash` 是 `position:fixed; inset:0; z-index:5` 的整屏径向渐变，中心色 `color-mix(dusk-cream 92%, white)` 接近纯白，动画 `lbPortalReveal 700ms cubic-bezier(.32,.72,0,1)` 把 `clip-path` 从 `circle(0%)` 扩到 `circle(150%)` —— 该曲线前快后慢，整屏在约 200ms 内被盖满，opacity 还要到 62%（≈434ms）才开始降。于是 0→950ms 屏幕上只有转圈按钮和离场的卡片（停顿），950ms 之后近白层糊满全屏再慢慢撤掉（闪）。反方向的退出登录（`resetStage()`）本来就没有 `.wash`，只靠一组 opacity 过渡，用户要的正是那一种。
- 原因：950ms 这个数字是被"卡片 `is-leaving` 的 450ms 淡出要走完"挤出来的，而"要先有东西遮住才能淡入"又强迫金幕与 `data-stage` 同帧触发。整屏不透明层与"平滑"本身就冲突：盖满 = 亮度突变，62% 前不透明 = 主页面该淡入的 620ms 里前 434ms 被完全挡住。
- 解决方法：进入方向改成纯交叉淡入，只做减法。`enter()` 的时序改为 0 提交 → 420ms `card.is-leaving` → 700ms 翻 `body[data-stage]` → 1320ms `hideStage()`（总时长 1.68s → 1.32s）；删 `templates/index.html` 的 `#transitionWash` 节点、`login.js` 里 `wash`/`arch`/`archExhibit` 三个常量与读 `arch.getBoundingClientRect()` 写 `--rx/--ry`、加 `revealing` 的那一段、`resetStage()` 里对应的两行 `classList.remove`；删 `login.css` 的 `.wash` 规则块、`@keyframes lbPortalReveal`、`.arch-exhibit.awake .arch` 规则块与 reduce-motion 里的 `.wash.revealing` 那条。淡入规则一条都没新增：`.page` / `.bg-mist` / `.bg-vignette` 本来就是 `opacity .62s`，`.portal` / `.site-foot` / `.backdrop` 本来就是 `opacity 520ms`，退出方向一直在用同一组规则，改完两个方向合一，`prefers-reduced-motion` 分支（`rm-out` 150ms 淡出）也不再与主路径分叉。
- 日期：2026-09-22
- 验证：临时实例 5001（未占 5000），一次性用户 `pytest13`。**结构核对（与渲染无关，可信）**：加载后的页面遍历全部 `styleSheets`，选择器匹配 `wash|lbPortalReveal|awake` 的规则 0 条；`#login-gate` 内 `position:fixed` 且 opacity>0.9 的后代 0 个（整屏遮挡层彻底不存在，"闪"的来源被移除）；`.page` 计算 transition = `opacity 0.62s cubic-bezier(.22,1,.36,1)`、`.portal` = `opacity 520ms cubic-bezier(.32,.72,0,1)`，即两个方向共用同一组淡入淡出规则。12 个模块 `node --check` 全过，控制台无报错。**功能核对**：`MutationObserver` 观测到事件顺序是 `card.is-leaving` → `data-stage=app` → `gate.hidden`；点退出登录后 `data-stage=login`、登录台重新可见、卡片类复位成 `login-card`、`body.login-pending` 恢复，再进入一遍顺序不变。**注意**：本次浏览器是后台不可见标签页，Chrome 把定时器钳到 ≥1s，实测到的三个时刻是 854 / 854 / 1844ms（源码排程 420 / 700 / 1320ms 被钳到一起），所以**转场的实际观感需要用户在自己的前台窗口里看一眼**再定稿。
- 未做：A2（登录卡整体推移 550ms）、A3（View Transitions API）随本条一并否决 —— 前者是大位移、与"朴素"相反，后者同样要先盖一层快照，且局域网 http 非安全上下文下 Firefox/Safari 不支持，要写降级分支。

## 主页面右侧滚动条隐藏

- 问题：主页面右侧一直挂着一条浏览器滚动条，用户不需要它（"详情页右边有个 side bar 我不需要这个"）。
- 原因：`ui.css` 只给了 `html, body { overflow-x: hidden }`，纵向滚动仍走文档滚动条；文件里那条 `.no-scrollbar` 工具类全项目没有任何地方引用，等于没生效。
- 解决方法：`static/css/ui.css:16-19` 删掉无人使用的 `.no-scrollbar` 两条规则，换成文档级 `html { scrollbar-width: none; -ms-overflow-style: none }` + `html::-webkit-scrollbar { display: none }`。只作用在 `html` 上，所以弹窗 `.modal-box`（`overflow: auto`）和登录台 `.stage-scroll` 自己的滚动条不受影响。
- 日期：2026-09-22
- 验证：临时实例 5001。改动前 `innerWidth - documentElement.clientWidth` = 15px、`scrollbarWidth` 计算值 `auto`；改动后两者为 **0px / none**，`window.scrollTo(0,300)` 后 `scrollTop > 0`（滚动本身照常，滚轮与方向键可用），`scrollHeight 648 > clientHeight 546` 证明确实处于可滚动态。

## 登录改秒登：提交即交叉淡入，1.32s → 0.48s

- 问题：用户反馈"登录是不是有点稍微慢了，能不能秒登"。实测点「进入」后要 1.32s 主页面才完全出现，而这 1.32s 里没有任何网络等待。
- 原因：上一条（T-1）定的排程是 0 按钮加载态 → 420ms 卡片离场 → 700ms 翻 `data-stage` → 1320ms 收幕。0→420ms 屏幕上只有一颗转圈按钮，可 `ctx.setUsername()` 在第 0 毫秒就把文件列表和留言板拉起来了，那 420ms 是纯空等；主页面又晚到 700ms 才开始 `.62s` 淡入。网络侧不是瓶颈：20 个静态请求最晚 86ms 结束，TTFB 11ms、`DOMContentLoaded` 83ms、`load` 87ms。
- 解决方法：`login.js` `enter()` 去掉那三段延时，改成**提交后立即 `document.body.dataset.stage = 'app'`，`later(hideStage, 480)`**，主页面淡入（`.page` `.62s`）与登录台淡出（`.portal` / `.site-foot` / `.backdrop` `520ms`）同一帧开始，480ms 收幕（按 `.portal` 的 `520ms cubic-bezier(.32,.72,0,1)` 与 `.page` 的 `.62s cubic-bezier(.22,1,.36,1)` 算，480ms 时两条曲线都已走到 ~99%，收幕等于 invisible）。顺手清掉因此变成死代码的部分：按钮的 `is-loading` 状态（没有网络请求就不该假装在转）—— 删 `templates/index.html` 的 `.btn-spinner` 节点与 `id="loginBtn"` / `id="btnLabel"`、`login.css` 的 `.btn-spinner` 与三条 `.is-loading` 规则和 `@keyframes lbSpin` 与 `.enter-btn:disabled`、`login.js` 的 `btn` / `btnLabel` 常量与 `resetStage()` 里对应的三行复位；`.login-card.is-leaving` 规则与卡片那条 `transition` 也一并删（卡片不再单独离场，跟着 `.portal` 整组淡出）。"记住我"命中时仍是 `init()` 里直接 `hideStage()`，零转场。
- 日期：2026-09-22
- 验证：临时实例 5001（未占 5000），一次性用户 `pytest13`。替换 `window.setTimeout` 后点按钮，抓到的延时从原来的 `[420, 700, 1320]` 变成 **`[480]`**（另三个 200 是 toast 自动关闭）；`MutationObserver` 记录 `data-stage` 翻成 `app` 发生在**提交后 3ms**。点退出登录复位正常：`data-stage=login`、登录台可见、卡片类为 `login-card`、`body.login-pending` 恢复、输入框已清空且拿到焦点；再进一次延时仍是 `[480]`。计算值 `#login-gate .portal` transition-duration = `0.52s`、`.page` = `0.62s`；DOM 里 `.btn-spinner` 已不存在。12 个模块 `node --check` 全过，控制台无报错。**注意**：本次浏览器是后台不可见标签页，Chrome 把定时器钳到 ≥1s（实测收幕落在 1057ms），480ms 的实际观感需用户在前台窗口看一眼。
