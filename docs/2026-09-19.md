## P0：直接伤"稳定传输 / 数据安全"

### P0-1 下载内存上限与"支持 30GB"宣称矛盾

- 问题：分片下载把整份文件在 JS 堆里存约 3 份——每个分片的 `arraybuffer` 全量留在 `chunkData`、再 `new Uint8Array(totalLength)` 申请一块完整连续内存、再 `new Blob([result])` 拷一次；峰值约 2~3 倍文件大小。单个 ArrayBuffer 还有浏览器硬上限（Chromium 故意让 ≥2GiB 的分配失败），实用上限约 1GB，超过则 `RangeError: Array buffer allocation failed`——而且失败发生在全部分片下完之后，等于白下一场。与页面宣称的"支持 30GB"直接冲突。
- 原因：下载路径设计（页内组装）与内存约束冲突。浏览器不允许 JS 流式落盘（服务是局域网 `http://`，非安全上下文，`showSaveFilePicker` 不可用，详见"候选改进"里的对照说明），所以"页内组装"必然把整份文件放进内存。
- 解决方法：按大小分流。阈值 `NATIVE_DL_LIMIT = 1GB`——≤1GB 保留页内分片并行（有进度条与速度显示），>1GB 走 `/api/download` 交给浏览器下载管理器（流式落盘、无内存上限、支持断点续传），页面提示去浏览器下载栏看进度。校验码弹窗内新增"命令行下载"区（curl 与 `aria2c -x4 -s4 -c`，URL 取 `location.origin`，配复制按钮），并提示 localhost 打开时需换成局域网 IP。只改前端，后端零改动。
- 日期：2026-09-19
- 验证：`/api/download` 返回正确的 Content-Length、`Accept-Ranges: bytes`，Range 请求 206；中文名走 `filename*=UTF-8''`；curl `-r` 取前 1MB + `-C -` 补完、aria2c `-x4 -s4 -c` 下载 64MB，结果 SHA-256 均与源一致。

### P0-2 `filename` / `username` 未过滤，路径可越出用户目录

- 问题：`username`、`filename`、`file_id` 被直接拼进存储路径，未做任何校验，可构造 `../` 读写用户目录之外的文件。涉及 `/api/file/info`、`/api/file/hash`、`/api/download/chunk`、`/api/delete`、`/api/download`、上传文件名（multipart）与 merge 的 filename，以及 `get_clipboard_path` / `get_user_files_dir` 两处目录拼接。
- 原因：早期只实现功能，没有输入校验层；所有路径都是裸 `os.path.join`。
- 解决方法：新增三个校验器并在全部 11 个接口入口统一使用——`normalize_username`（`^[\w-]{1,64}$`，`\w` 含中文）、`safe_filename`（拒绝路径分隔符、`..`、`.` 开头即隐藏文件）、`_FILE_ID_RE`（`^[A-Za-z0-9]{1,64}$`），非法一律 400。副作用（已确认可接受）：用户名不再允许空格和点，现有用户名均兼容。
- 日期：2026-09-19
- 验证：`username=../foo`、`filename=..\..\x`、`filename=.hashes.json`、`filename=..`、JSON body 里的 `..\` 删除请求全部 400；正常文件（含 `it's & test #1.txt`、中文名）的列表 / 校验 / 下载不受影响。

### P0-3 文件列表渲染未转义文件名（XSS / 属性截断）

- 问题：`loadFiles` 拼 HTML 时裸插 `${f.name}`（还包括 `title` 属性），并把它拼进内联 `onclick` 字符串；只有单引号被替换。含 `"` 或 `'` 的文件名可截断属性，理论上可注入。
- 原因：字符串拼接生成 DOM，展示层没有转义约定。
- 解决方法：文件行改为 `data-filename="${escapeHtml(f.name)}"`，点击行为改由 `#fileList` 事件委托按 `closest()` 路由（下载 / 删除 / 校验码），内联 `onclick` 全部移除，文件名展示统一走 `escapeHtml`。
- 日期：2026-09-19
- 验证：浏览器实测 `it's & test #1.txt` 渲染正确、委托点击能打开弹窗且命令 URL 编码正确、页面已不存在 `onclick` 属性。

## P1：对"快捷、稳定"体验影响明显

### P1-4 上传/下载没有取消按钮

- 问题：`uploadXhrs` 收集了 XHR 但没有任何 UI 调 `abort()`；下载的 XHR 干脆没收集。传大文件时用户只能看着，取消只能刷新页面（分片会残留）。
- 原因：只实现了传输与进度，没做中断路径。
- 解决方法：进度区新增"取消传输"按钮（传输开始显示、结束隐藏）；`cancelTransfer()` 统一 abort 当前传输的所有 XHR；上传侧附带调 `/api/upload/abort` 清掉已上传分片；取消后跳过重试、批量上传中止后续文件，状态提示"已取消"。
- 日期：2026-09-19（按钮与前端统一 abort，后端 abort 接口）
- 验证：浏览器实测 1GB 上传中途点取消——分片目录被清理、无半成品文件、按钮隐藏、输入框恢复可用。
- 遗留：取消作用于"当前传输"的语义仍有问题，见根目录 R3-P1-1。

### P1-5 孤儿分片目录无人清理

- 问题：`cleanup_chunks` 只在合并成功后调用；合并失败、浏览器中途关闭都不清理；启动对账也不碰 `.chunks`——分片目录会一直堆积。
- 原因：只考虑了成功路径的清理。
- 解决方法：三条清理路径——(1) 启动维护线程 `sweep_stale_chunks()`：删除"目录内最新文件 mtime 超过 24 小时"的分片目录（活跃上传会持续写新分片，不会误删）；(2) 取消上传调 `/api/upload/abort` 即时清理；(3) `merge_chunks` 失败时清理半成品文件与分片。
- 日期：2026-09-19
- 验证：启动清扫实测——3 天前的分片目录被删、新鲜目录保留；abort 接口实测分片目录即时消失。

### P1-6 端口双绑没有守门（踩过的坑）

- 问题：Windows + waitress 下两个进程能同时绑 5000（SO_REUSEADDR 语义），旧实例还在跑时新代码"改了没生效"，且没有任何提示。
- 原因：启动流程固定绑 5000，启动前不做检测；Windows 的 SO_REUSEADDR 语义允许重叠绑定。
- 解决方法：启动入口新增 `check_port_in_use(5000)`，发现端口已被占用则打印排查指引（`netstat -ano | findstr :5000` 找 PID、`taskkill /PID <PID> /F`）并 `sys.exit(1)`，不再静默双绑。
- 日期：2026-09-19
- 验证：占住 5000 后启动——退出码 1、提示文案正确。

### P1-7 启动脚本与入口体验缺口

- 问题：代码提示使用 `run_server.bat`，但仓库里没有这个文件；`gethostbyname` 只打印一个 IP（本机有 VMware/WSL 虚拟网卡时会打错那个）；不自动打开浏览器；没有 README。
- 原因：入口体验从未专门处理；IP 获取用了最简单的 API。
- 解决方法：(1) 启动横幅枚举全部局域网 IPv4，并用 UDP connect（不实际发包）找出默认路由出口 IP 标为"推荐"；(2) 监听就绪后延迟 1 秒自动打开浏览器（`threading.Timer` 不接受 daemon 参数，需构造后赋值）；(3) 新增 `README.md`；(4) 移除代码中对 `run_server.bat` 的提示——曾试做 `.bat`，实测发现 cmd 按 GBK 解析批处理、UTF-8 中文行会被当命令执行，用户明确否决，已删。
- 日期：2026-09-19（横幅/自动开页，README）
- 验证：本机实测枚举出 3 个 IP（2 个虚拟网卡 + 198.51.100.7），"推荐"标记正确；启动后 `GET /` 返回 200、各 API 正常。

### P1-8 `/api/download` 与其他接口的目录基准不一致（CWD ≠ 项目目录时下载 404）

- 问题：`send_from_directory` 把相对目录拼到 `app.root_path`（py 文件所在目录），而其余接口用的是进程 CWD 的相对路径。从项目目录启动时两者恰好一致，一旦从其他目录启动（如 `python E:\...\http_messages_share.py`、计划任务），上传/列表/删除落在 CWD 的 `files/`，下载却去 `app.root_path/files/` 找——表现为"列表里有文件，点下载 404"。
- 原因：Flask 的 `send_from_directory` 与手写路径解析的基准不同，两套基准混用。
- 解决方法：`CLIPBOARD_DIR` / `FILES_DIR` / `LOG_DIR` 统一锚定到 `os.path.dirname(os.path.abspath(__file__))`。
- 日期：2026-09-19
- 验证：从外来目录（`%TEMP%`）启动服务，列表与 `/api/download` 一致且内容哈希匹配。
- 备注：这是测 P0-1 时顺带发现的隐藏 bug。

## P2：优化项与低风险瑕疵

### P2-8 分片上传多一次磁盘写（multipart spool）

- 问题：32MB 分片走 multipart，Werkzeug 先把整片 spool 到临时文件，再 `copyfileobj` 到 `chunk_*`——每个字节写盘两次，合并时再读一次。
- 原因：multipart 解析路径决定了必然经过临时文件。
- 解决方法：改为裸 body 上传——前端 `xhr.send(blob)`，`file_id` / `chunk_index` 走 `X-File-Id` / `X-Chunk-Index` 请求头，后端直接读 `request.stream` 写盘。注意 `username` 必须走 query（HTTP 头只允许 latin-1，中文用户名放头里会炸）。
- 日期：2026-09-19
- 验证：先测再改——multipart 基线 1GB 端到端 82.3 MB/s（分片阶段 102.2 MB/s，低于千兆线速 118；合并阶段纯磁盘 421.7 MB/s，证明瓶颈在双写）；改裸 body 后分片阶段 389.0 MB/s、端到端 **237.4 MB/s（2.9 倍）**，SHA-256 一致。
- 遗留：协议变更导致旧页面不兼容，见根目录 R3-P0-2。

### P2-9 剪切板写入非原子

- 问题：`write_clipboard` 直接 `open('w')` 覆盖写，进程被杀可能截断原文件。
- 原因：写文件没有走原子替换。
- 解决方法：临时文件 + `os.replace` 原子替换（与 `write_hashes` 同款模式）；写入失败照常返回 500，不静默吞掉用户数据。
- 日期：2026-09-19
- 验证：写入/回读一致，无 `.tmp` 残留。

### P2-10 上传/下载共用同一条进度条与同一个 `progressTimer`

- 问题：进度条 DOM 与 `progressTimer` 全局共享，并发传输时互相覆盖。**真正的 bug 比"显示覆盖"更重**：全局 timer 句柄被第二次传输覆盖后，第一个 interval 再无人清除——双 tick 互踩，且该 interval 会每 200ms 改一次 DOM 直到刷新页面，闭包连同 `chunkData` 一起泄漏。
- 原因：传输状态用了模块级单例，并发时相互踩踏。
- 解决方法：改为每次传输持有局部句柄（`uploadTimer` / `downloadTimer`），各自在完成与失败分支里清自己那个。"共享进度条后来者覆盖显示"按简易项目定位保留。
- 日期：2026-09-19
- 验证：代码复核确认句柄已局部化、各终态自清。
- 遗留：`transferXhrs` / `transferCancelled` / `activeTransferId` 三个状态仍是模块级单例，见根目录 R3-P1-1。

### P2-11 `/api/upload` 是前端已不用的死代码

- 问题：前端只走 `/api/upload/chunk` + `/api/upload/merge`，`/api/upload` 无人调用，且其重名处理与 `merge_chunks` 重复。
- 原因：分片方案上线后旧的整体上传接口没有清理。
- 解决方法：删除该接口（用户确认），连带删除仅它使用的 `check_disk_space`。
- 日期：2026-09-19
- 验证：`POST /api/upload` 返回 404。
- 备注：这次连带删除让"主路径从来没有过磁盘空间检查"这一既有缺口显形，见根目录 R3-P0-1。

### P2-12 `/api/download/chunk` 的 Range 解析不严谨

- 问题：`bytes=-500` 后缀语义被当成"取前 500 字节"（应取末 500）；非数字 Range 抛 `ValueError` → 500（应 416）；未校验 `start ≤ end`（可产生负数长度）。
- 原因：Range 解析只按 `bytes=start-end` 一种形态做 `split`。
- 解决方法：完整解析——支持后缀 `bytes=-N` 取末 N 字节，负 start、倒序、非数字、空区间一律返回 416。
- 日期：2026-09-19
- 验证：`bytes=0-9` → 206 前段、`bytes=-10` → 206 末 10 字节（Content-Range 正确）、`abc` / `99-1` / `-0` 全部 416。

### P2-13 重名去重只做一层、时间戳秒级碰撞

- 问题：已存在同名文件时只追加一次秒级时间戳；同一秒内第二次同名上传会命中同一个 `名字_时间戳`，`open('wb')` 直接覆盖前者，并把哈希记录改写成新文件的——旧文件不可恢复。
- 原因：重名处理只有"加一层时间戳"，且用覆盖写。
- 解决方法：新增 `exclusive_path()`（原名 → 时间戳 → 时间戳_1 → 时间戳_2 … 循环到空闲）+ `open(file_path, 'xb')` 独占创建；并发抢先时宁可报错也不覆盖。
- 日期：2026-09-19（起，定型）
- 验证：同秒两次同名合并产出 `dup.txt` 与 `dup_1789806230.txt`，内容互不覆盖；第三轮复审再验——同名两次上传得到 `dupe.bin` + `dupe_1789809234.bin` 并存，各 512KB，SHA-256 均与源文件一致。
- 遗留：`open('xb')` 失败路径可能删除他人文件，见根目录 R3-P1-3。

### P2-14 merge 信任磁盘上的分片集合

- 问题：merge 只合并 `.chunks` 里实际存在的文件，缺片不报错，会产出被截断的文件并记上"完整哈希"；对不存在的 file_id 调用还会因 `get_chunk_dir` 创建目录而产出 0 字节文件并显示"上传成功"。
- 原因：接口没有防线，完全信任磁盘状态与客户端行为。
- 解决方法：与 P2-20 一起闭环——merge 请求必须带 `total_chunks`，后端校验分片序号恰为 `0..N-1` 无缺失，缺片返回 400「分片不齐全」并清理分片目录，不再产出截断文件。
- 日期：2026-09-19（校验，前端补发 `total_chunks`）
- 验证：空分片目录 merge 5 片 → 400「分片不齐全: 期望 5 片，实收 0 片」，0 字节假文件问题消失。
- 遗留：`total_chunks` 无上限，见根目录 R3-P1-2。

### P2-15 启动对账可能与早期传输抢磁盘 I/O

- 问题：后台线程给无记录文件补算 SHA-256（全量读盘），理论上会与早期传输抢 I/O。
- 原因：对账在启动时无条件扫描。
- 决定：**不做。** 已有 mtime + size 的跳过机制，实测日志"补算 0 个、耗时 0.00s"，重启基本无活干；仅在大量未记录文件时才会明显，收益不足以支撑额外复杂度。
- 日期：2026-09-19

### P2-16 访问日志逐请求记录，大文件会产生大量分片日志行

- 问题：30GB 下载约 960 条分片日志行，属噪音（有滚动 20MB×5，不会爆盘）。
- 原因：访问日志对所有请求一视同仁。
- 解决方法：分片路径（`/api/upload/chunk`、`/api/download/chunk`）请求日志降为 DEBUG，完成 / 合并 / 中断等关键事件保持 INFO。
- 日期：2026-09-19
- 备注：dev 服务器另有 werkzeug 自带访问日志（不受此控制）；生产 waitress 无此噪音。代价是分片级观测更少，见根目录 R3-P2-3。

### P2-17 错误响应把 `str(e)` 原样返回给客户端

- 问题：兜底异常处理与多个 `except` 块把 `str(e)` 回给客户端，会泄漏服务器内部路径。
- 原因：错误处理以"能看到原因"为先，没有区分客户端可见信息与服务端日志。
- 解决方法：兜底 handler 与各 `except` 块改为固定友好文案，堆栈与细节只进日志；自产的业务错误文案（如"分片不齐全"）保留原文。
- 日期：2026-09-19
- 核对：`upload_merge` 与 `delete_file` 两处遗漏，见根目录 R3-P2-5。

### P2-18 无 favicon

- 问题：每次页面加载多一条 404 日志，纯噪音。
- 原因：页面从头到尾没提供图标，浏览器按惯例请求 `/favicon.ico`。
- 解决方法：`<head>` 加 data-URI SVG 图标，零额外请求。
- 日期：2026-09-19

### P2-19 分片重试只有一次、无退避

- 问题：失败后立即重试一次，网络抖动时容易连环失败；叠加"无取消按钮"时用户只能干等。
- 原因：重试逻辑没有退避。
- 解决方法：重试前加 300ms / 800ms 退避，取消时立即中止不再重试。
- 日期：2026-09-19

### P2-20 `total_chunks` 字段收了但服务端没用

- 问题：接口收下 `total_chunks` 只做回显，merge 完全信任磁盘状态（与 P2-14 同源）。
- 原因：该字段是分片协议早期加上的，但服务端从未把它接入校验逻辑。
- 解决方法：合并请求改为必带 `total_chunks`（前端补发），作为 P2-14 防线的输入；缺失或非法返回 400。
- 日期：2026-09-19（前端，后端校验）

- 解决方法:第一批演示落在 `demo-v1/深蓝/`(纯静态单文件,零外部依赖,不请求后端),内含 `index.html` 与 `README.md`。设计:深色锁定、单一 accent 蓝 `#5ea0ff`、等宽数字、内联描边图标 sprite;把 review-issues 里 4 条产品级建议画进了界面(磁盘水位、页面内一键校验、`?u=` 分享链接 + 二维码、多文件排队上传)。方案确认前 `templates/index.html` 不动。后续竞稿扩到 `demo-v1/`(6 稿)、`demo-v2/`(4 稿)、`demo-v3/`(2 稿),定稿为 `qfs-waterlilies/`,生产资产复制进 `static/`。
- 注:这些目录含 1~1.7MB 的参考图与截图,共约 13.7MB,2026-09-21 决定不入库(写进 `.gitignore`),只在本地留存。
