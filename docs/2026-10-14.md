## 转公开前脱敏：改成"回调重放"，工作区与历史同源（A-1014-1 前半）

- 问题：要把仓库从私有转公开。逐项扫描受版本控制的文件，查出四类会跟着公开的本机信息：① 局域网 IP（4 份 `docs/` + `design-archive/` 竞稿页，共 8 处）；② 真实登录用户名与第二个身份词（AGENTS.md、review-issues.md、6 份归档、2 处代码：控制台横幅与 logger 名；另散布在 10 个竞稿页的假数据里）；③ Windows 账户名与项目绝对路径（`design-archive/qfs-waterlilies/` 三份设计工具产出的 JSON 共 42 处 + 1 份 spec）；④ git 历史本身（见下一条）。
- 原因：归档当初按仓库规矩"验证要写实测数字"，把当时的真实 IP、用户名、本机路径直接写进记录；`design-archive/` 是整目录入库的，工具产物里的绝对路径没人看过。第一轮我按"整词命中"手工点改，**漏了 10 个竞稿文件**（它们同样含真实 IP 与用户名），手工方式在这种分散场景不可靠。
- 解决方法：改为**规则回调**——一组按顺序生效的映射（IP→RFC 5737 为示例保留的地址段；两个身份词→假名 `用户`/`同事`；控制台横幅去身份化；logger 名缩短；家目录→`<HOME>`、项目根→`<PROJ>`；每条同时覆盖 JSON 双反斜杠与纯文本单反斜杠两种落盘形态），先用它重扫工作区（改动 30 个文件），再验证：`git show HEAD:<文件>` 的旧内容过一遍回调，与扫描后的工作区**逐字节比对**，33 个抽样文件一致（仅 AGENTS.md / README.md / review-issues.md 三处差在我当天新增的章节，属预期）。
- 回调脚本放哪：**仓库外的本机临时目录**。我一开始把它写进 `tools/`，是错的——规则里的匹配模式本身就字面写着待清除的旧值（账户名、项目绝对路径、邮箱），提交进仓库等于把这些值重新公开一遍。写完立刻用"待提交内容里 grep 旧值"这一步发现并撤出。
- 回调自己咬了自己一口：最后一条"残余账户名 → 占位符"的兜底规则太宽，把有意公开的 GitHub 账号名也吃掉了——`LICENSE` 版权行变成 `<账号>-Y`、本文件那行邮箱变成 `<账号>-Y@users.noreply.github.com`，共 2 处。已修（署名还原、邮箱改写为不含具体账号的形式），并把该规则改窄为**只匹配"用户目录根 + 账户名"这种路径形态**，不再碰独立账号名。（注意：这条记录本身不能举出该路径的字面写法，否则回调重放时会咬到自己——我这行最初就踩了这个。）重写基线里没有这两个新建文件，历史未被波及，无需重跑。
- 验证判据（可复现，三条并用）：
  - **提交数用备份 bundle 比对**，不用减法猜：原始 53 笔的提交信息在新历史里 53/53 全存在（一条不少）。此后 master 每加一笔总数就会变，所以记录只锚定"原始 53 笔全保留"这个不变量，不写会漂移的总数。
  - **`git log -S<旧值>` 会虚报**：它把"我写进去又删掉"的 diff 也算命中（真名一度报 2 命中，全是我的修复提交自身）。改用逐树检查——遍历 `master` 全部提交做 `git grep`：私有网段完整地址、旧邮箱、真实姓名、项目绝对路径、logger 旧名、第二身份词**六项均为 0 个树含该值**。
  - **对象库级审计**（`git cat-file --batch-all-objects --batch` 全量搜）：私有网段地址 / 项目绝对路径 / logger 旧名 / 第二身份词 = 0 命中；旧邮箱与真名各剩 2 命中，`git fsck --no-reflogs --unreachable` 证实这 2 处全在 4 笔悬空提交里——是我自己重写过程中产生又丢弃的中间提交，从任何 ref 不可达，**推送时不会上传**；本地 reflog 保留它们以便回退，暂不清除。剩余"账户名"命中全部来自有意公开的 GitHub noreply 邮箱与署名。
- 第三遍重写统一署名：`--name-callback 'return b"qyy"'`，现全部提交（重写来的 53 笔 + 之后新增）署名为 `qyy <GitHub noreply 邮箱>`（原先 4 个早期提交带真实姓名）。跑这一遍前先验了回调**幂等性**——结果它确实不幂等：我这行归档里举了一句"用户目录 + 账户名"的字面形态，被兜底规则重新改写。改掉举例写法、确认"改动 0 个文件"后才动手。教训：**归档文字不能保留刚清除的旧值字面量**，否则既重新泄露、又让回调重放时咬到自己（真实姓名那处同理，写在台账里就成了第 6 个命中）。
- 为什么先验证这一步：重写历史要用同一个回调。若两套规则产出不同内容，历史与 HEAD 会出现裂缝，"脱敏"就变成半成品。回调本身也在这轮被抓出两处缺陷（双反斜杠少一层转义导致 JSON 路径没命中；替换串以反斜杠结尾被 `re.sub` 当转义起始）——没有这个对照测试就不会发现。
- 备份：改动前的 7 份文件 + 全历史 bundle 各一份（`%TEMP%\qfs-desensitize-backup\`、`%TEMP%\qfs-history-backup-20261014-135320.bundle`，13.8MB）。

## 发布：删库重建关闭泄露面，1.3 上线

- 问题：force-push 之后实测——旧提交 `819bb1c` 虽已无任何 ref 指向，GitHub 仍按 SHA 提供内容（我用只读 API 从旧树取回 `docs/2026-09-19.md`，里面 `198.51.100.7` 命中 1 次）。仓库转 public 后，这个后门就从"知道 SHA 的人"扩大到任何人。
- 原因：git 服务端不会因为 ref 移动就立刻丢弃不可达对象，GitHub 的孤儿对象仍可通过完整 SHA 访问。
- 解决方法：用户手动删除 GitHub 仓库 → `gh repo create` 同名重建（私有）→ 首推 `master` + `1.0/1.1/1.2/1.3` 四个 tag → 核验 → 切 public。重建后新仓库的对象库只含重写历史（60 个提交）。
- 验证（陌生人视角，四条并用）：
  - 从远程全新 `git clone` 后逐个搜旧值：三个局域网 IP 形态、旧邮箱、真实姓名、项目绝对路径、logger 旧名、第二身份词——**7 项全部 0 命中**；克隆内署名唯一 `qyy <GitHub noreply>`。
  - 旧 master/旧 tag 的 SHA 按 API 取内容：取不到（`No commit found for SHA`、旧 IP 命中 0）。
  - 不带凭据访问 `https://github.com/.../commit/819bb1c…`：**HTTP 404**。
  - 远程现 6 个 ref 全指向重写后的对象；当前 master 上的四份归档文件旧值命中 0。
- 判据教训：我第一版"旧 SHA 是否失效"的测试写松了——GitHub 报错返回 422 而非 404，被我的关键词匹配放过，误报成"仍可访问"。改用"能否真取回旧内容"作判据才对。
- GitHub Release：1.3 已单独建（Release 是网页层产物，`git tag` 不产生它）。地址见仓库 Releases 页。
